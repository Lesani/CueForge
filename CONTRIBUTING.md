# Contributing to CueForge

Thanks for your interest in improving CueForge! This guide covers how to get a
development environment running, how to test your changes, and what to expect
when opening a pull request.

## Development setup

CueForge runs on Windows and Linux (x86_64 and aarch64) with Python 3.13.
Paths below are written for both; substitute `.venv/bin/python` for
`.venv/Scripts/python.exe` on Linux.

On Linux, install PortAudio first — `sounddevice` publishes no wheel carrying
it, so it must come from the package manager (`libportaudio2` on Debian/Ubuntu,
`portaudio` on Fedora/Arch).

```sh
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

`ffmpeg` is downloaded automatically on first use, so no manual install is
required. To run the app straight from source:

```sh
.venv/Scripts/python.exe -m cueforge
```

Then open the printed URL (default http://localhost:7070/). The web UI has **no
build step** — it is plain ES-module JavaScript served directly from
`cueforge/web/`, so edits are picked up on reload.

## Running the tests

Python suite (mixer/fades, project model + storage, import/dedup, cue traversal,
server reducer):

```sh
.venv/Scripts/python.exe -m pytest
```

A handful of tests shell out to a real `ffmpeg` and fail without one (this is
what CI's provisioning step is for). Fetch it once up front to run the whole
suite locally:

```sh
.venv/Scripts/python.exe -c "from cueforge import ffmpeg_util; print(ffmpeg_util.download_ffmpeg())"
```

Web unit tests (run with Node's built-in test runner):

```sh
node --test "tests/web/**/*.test.mjs"
```

Please make sure both suites pass before submitting a change, and add tests for
new behavior where it is reasonable to do so.

Testing is intentionally focused on core logic: the mixer/fades, project model
and storage, import/dedup, cue traversal, the server state reducer, and the
self-updater.

## Project layout

```
cueforge/
  __main__.py        # `python -m cueforge` entrypoint -> launcher
  launcher.py        # console dashboard, PIN, QR, browser, uvicorn
  audio_format.py    # sample rate / channels / dB helpers
  platform_util.py   # OS/arch identity: exe suffix, arch tag, asset names
  ffmpeg_util.py     # locate/auto-download the ffmpeg binary
  ytdlp_util.py      # locate/auto-download yt-dlp (YouTube import)
  update_util.py     # GitHub Releases check + binary self-update
  engine/            # real-time NumPy mixer (normal/background/audition, panic)
  project/           # show model, importer, .cueforge storage, traversal
  server/            # FastAPI app, WebSocket protocol, show controller/reducer
  web/               # vanilla-JS UI (index.html, css/, js/) — no build step
scripts/             # make_demo_show.py, make_icons.py, PyInstaller runtime hooks
tests/               # pytest suite (engine, project, server, updater, platform)
build_exe.py         # PyInstaller build script
requirements.txt
```

The WebSocket/REST protocol is documented in
[`cueforge/server/PROTOCOL.md`](cueforge/server/PROTOCOL.md). ffmpeg is
resolved in this order: `CUEFORGE_FFMPEG` env var, download cache
(`~/CueForge/bin`), `vendored/` beside the binary, `vendor/ffmpeg/` in the repo.
There is deliberately **no** fallback to an ffmpeg on `PATH`: the MP3 export
needs `libmp3lame`, which plenty of distro builds omit, so CueForge only uses a
build it fetched itself. Which build that is depends on the platform —
gyan.dev's `release-essentials` zip on Windows, BtbN's `gpl` static tarball on
Linux — see the module docstring in `cueforge/ffmpeg_util.py`.

Anything that varies by OS or CPU belongs in `cueforge/platform_util.py`, not
in a fresh `os.name == "nt"` test at the call site. That module is the single
place the ffmpeg resolver, the yt-dlp resolver, the self-updater, and
`build_exe.py` agree on what this build is called and which assets match it.

## Building the executable

```sh
.venv/Scripts/python.exe build_exe.py      # or ./build.sh / build.bat
```

Output is named for the platform, matching the release asset the in-app updater
looks for: `dist/CueForge.exe` on Windows, `dist/CueForge-linux-x86_64` (or
`-aarch64`) on Linux — a single-file console app that opens the browser and
prints the URL/PIN/QR. If a `vendor/ffmpeg/ffmpeg` (and/or `vendor/yt-dlp/yt-dlp`,
`.exe`-suffixed on Windows) is present, it is copied alongside as
`dist/vendored/` so the packaged app can run offline; otherwise the app
downloads what it needs on first use. The `.spec` file is regenerated by
`build_exe.py` — don't edit it by hand.

On Linux the build also bundles the system `libportaudio.so.2`, because
`sounddevice` ships no Linux wheel that carries PortAudio and locates its
library through `ctypes.util.find_library` — which searches `ldconfig`, never
the PyInstaller bundle. `scripts/pyi_rth_portaudio.py` is the runtime hook that
redirects that one lookup to the bundled copy; without it the binary would only
start on machines that already have `libportaudio2` installed.

> **Close any running CueForge before building.** PyInstaller cleans the output
> first; a running instance holds files open in `dist/` and a partial write can
> corrupt the bundle. If the binary ever serves `{"web":"no index.html yet"}`,
> its web assets were lost — rebuild cleanly. `build.bat` and `build.sh` do
> this for you.

Official releases are built by CI: pushing a `v*` tag runs the tests and builds
on all three targets (Windows, Linux x86_64, Linux aarch64), then publishes the
binaries with a combined `SHA256SUMS.txt` as a GitHub Release — the same
artifacts the in-app updater installs. The tag must match
`cueforge.__version__` and the `pyproject.toml` version or the build fails.

The Linux runners are pinned to Ubuntu 22.04 rather than `latest` on purpose: a
PyInstaller bundle links against the build machine's glibc and will not start on
anything older, so the oldest supported runner sets the compatibility floor.

## Code style

- **Python:** follow the style of the surrounding code (PEP 8, type hints,
  focused modules with clear docstrings). Keep functions small and testable.
- **JavaScript:** vanilla ES modules, no framework, no bundler. Match the
  existing structure under `cueforge/web/js/`.
- Keep changes focused. Unrelated refactoring is best kept in a separate PR.

## Pull requests

1. Fork the repo and create a feature branch from `main`.
2. Make your change, with tests and a clear commit message.
3. Ensure `pytest` and `node --test "tests/web/**/*.test.mjs"` both pass.
4. Open a pull request describing **what** changed and **why**. Link any related
   issue.

Small, well-scoped PRs are easier to review and get merged faster. If you are
planning a larger change, please open an issue first to discuss the approach.
